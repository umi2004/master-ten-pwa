公式文言は「adjacent horizontal, vertical and diagonal cells」とする一方、公式ヒント画像では、削除済みの空所を複数挟んだ縦方向のペアが提示されている。したがって、実際の接続判定は単なる8近傍ではなく、**同一直線上で、間に未削除数字がない最初の数字までを接続可能とする方式**である可能性が高い。ただし、空所越し接続の完全なアルゴリズムは文章では公開されていないため、「画像から観察可能」のBに分類する。citeturn20view1turn22view1

公式説明にある「become a master」「true master」は、熟達を意味する宣伝文句である。独立した「Master Mode」「Master Levels」「Master Series」という正式名称、入口、問題数、問題番号体系、平均手数、最大高さなどは、今回確認した公式サイト、ストア説明、公式ニュース、検索可能な公式動画・SNSでは確認できなかった。したがって、通常問題の仕様をEasybrain製品の「Master問題」へ流用してはならない。citeturn20view0turn20view1turn21search1

「Master Ten」については、Easybrain製品の非公開生成方式を推測して再現するよりも、次の独自構成を推奨する。

**固定9列、数字1～9、空所越し直線接続、明文化した行またぎ接続、全行消去時のみ行削除、残存数字の読み順追加、追加回数制限、seed付き決定論的生成、生成後ソルバー検証、難易度計測、厳選された固定Master問題と生成問題の混合**である。

問題生成は、完全ランダム単独ではなく、**逆向き生成またはテンプレート生成 → seedによる変形 → ソルバー検証 → 難易度評価 → 重複除去 → 一部手作業レビュー**というパイプラインが最も安全である。Easybrainがこの方式を採用しているという証拠はなく、あくまでオリジナル実装への提案である。

ソルバーはTypeScriptを前提に、盤面を`0=空所、1～9=数字`の固定幅配列として保持し、追加残数を状態へ含める。検証用は**メモ化付き反復深化DFSまたはIDA\***、最短解が必要な小規模問題にはA\*、ヒント用には検証済み解経路のキャッシュまたは時間制限付き探索を推奨する。A\*は評価関数を用いた最小コスト経路探索として定式化され、IDA\*はA\*型の閾値と深さ優先探索を組み合わせてメモリ使用を抑える方式である。citeturn19search0turn19search3turn24search1turn24search4

## 基本ルール・盤面構造・接続判定

**基本ルール**

Easybrainが公式に説明する目的は、盤面上の全数字を消すことである。消去できる数値関係は、同じ値、または合計10の二種類である。公式例には「1と1」「7と7」「6と4」「8と2」が示されている。citeturn20view0turn20view2

### 数字の範囲

公式文章は「使用値は1～9のみ」と明示していない。しかし、公式例と公式画像では1～9が使用され、0は確認できない。したがって結論は次のとおりである。

| 項目 | 結論 | 確認度 |
|---|---|---:|
| 観察された数字 | 1～9 | B |
| 0の使用 | 観察できず | D |
| 10そのものをセル値として使用 | 観察できず | D |
| 負数・二桁数 | 観察できず | D |

オリジナル実装では、ルールの簡潔性と補数関係を保つため、1～9に固定するのが妥当である。

### 同じ数字

```text
消去前                 消去後
[ 4 ][ 4 ]             [ × ][ × ]
```

4と4は同じ数字なので有効である。5と5は「同じ数字」と「合計10」の両条件を同時に満たすが、1回の通常ペア消去として扱うのが自然である。

### 合計10

```text
[ 6 ][ 4 ]  →  [ × ][ × ]

[ 8 ][ 2 ]  →  [ × ][ × ]

[ 3 ][ 7 ]  →  [ × ][ × ]
```

公式説明は、数字の順序を限定していないため、6→4でも4→6でも同じペアとして扱うのが妥当である。citeturn20view0

### クリア条件と敗北条件

全数字が取り除かれた時点で勝利することは公式に確認できる。citeturn20view0turn20view3

全消去以外の通常クリア条件は確認できない。ただしEasybrainの公式画像には「Goal」やスコア目標に見える表示があり、イベント・トーナメント・スコア競争では、全消去以外の評価目標が併存する可能性がある。これは画面観察にとどまり、通常ステージの勝利条件変更を示すものではない。citeturn12view1turn22view2

敗北またはゲームオーバー条件は公式文章に明記されていない。自然な候補は「有効ペアがなく、数字追加も使えない」であるが、Easybrainの確定仕様としてはDである。

**盤面構造**

### 列数

公式スマートフォン画像とタブレット画像はいずれも、盤面が9列に見える。画面幅が広いタブレットでも列数を増やさず、中央に固定幅の盤面を配置しているように観察できる。citeturn22view0turn22view3

したがって、9列はBである。公式文章で「常に9列」と明記されていないためAではない。

### 初期行数と可変性

公式画像の一部では、Stage 1の盤面におおむね8行が見える。しかし、画像が開始直後か途中状態かを完全には判定できず、全問題で共通する初期行数とも確認できない。citeturn22view0

手詰まり時に追加行を下部へ増やすことは公式に確認されているため、盤面の行数は少なくともプレイ中に可変である。citeturn20view0turn20view1

| 項目 | 結論 | 確認度 |
|---|---|---:|
| 列数 | 公式画像では9列 | B |
| 初期行数 | 画像では約8行の例がある | B |
| 全問題共通の初期行数 | 未確認 | D |
| 問題ごとの初期行数差 | 未確認 | D |
| 行追加による可変化 | あり | A |
| 最大行数 | 未確認 | D |
| 画面外へのスクロール | 明示情報なし | D |
| 固定盤面か可変盤面か | 列固定・行可変の可能性が高い | B/D |

### セルと削除状態

公式画像では、削除された数字が完全に消失するというより、薄い灰色の数字または空所として残り、同じ行の残存数字が横へ詰め直されていない。citeturn22view0turn22view1

```text
消去前
[ 2 ][ 3 ][ 8 ][ 2 ][ 5 ]

8 と 2 を消去
[ 2 ][ 3 ][ × ][ × ][ 5 ]
```

部分消去後の数字位置維持はBである。全セルを左詰めする挙動は観察されない。

Google Playの公式説明には「行を取り除くと+10点」とあるため、1行が完全に空になった際に、その行を取り除く概念がある。ただし、行を即時に上詰めするか、視覚上だけ非表示にするか、アニメーション終了後に処理するかは説明されていない。citeturn20view0

```text
行全体を消去した場合の候補

消去直後
[ × ][ × ][ × ][ × ][ × ][ × ][ × ][ × ][ × ]

考えられる処理
・行そのものを削除し、下の行を上へ移動
・論理上は残し、描画だけ折り畳む
・次の操作時に正規化する

Easybrainの厳密な方式：未確認
```

### 空白セルの内部表現

内部実装は非公開である。考えられる方式は、セル配列に削除フラグを持つ方法、0やnullを格納する方法、ビットマスクで生存状態を分離する方法などである。

「Master Ten」では、TypeScript上で次の論理表現を推奨する。

| データ | 推奨内容 |
|---|---|
| `width` | 9 |
| `cells` | 0を空所、1～9を数字とする一次元配列 |
| `logicalLength` | 最終使用セル位置 |
| `additionsRemaining` | 数字追加残数 |
| 行番号 | `floor(index / width)` |
| 列番号 | `index % width` |

これはEasybrainの内部方式についての主張ではない。

### モバイル縦画面とタブレット

公式スマートフォン画像では、上部にステージ、スコア、当日ベスト等があり、中央に盤面、下部に数字追加とヒントの丸型ボタンがある。citeturn22view0turn22view1

タブレット画像でも9列盤面を中央へ置き、周囲の余白を広くする構成が観察できる。citeturn22view3

正確なセルピクセルサイズは、画像解像度、端末倍率、ストア画像の縮尺が混在するため決定できない。「Master Ten」では、見た目のセルより大きなタップ領域を確保し、最低限のアクセシビリティを優先すべきである。

**接続判定**

### 水平・垂直・斜めの隣接

公式に認められている基本接続は、横、縦、斜めである。citeturn20view1turn20view2

```text
水平
[ 6 ][ 4 ]        有効

垂直
[ 7 ]
[ 3 ]             有効

右下斜め
[ 2 ][   ]
[   ][ 8 ]        有効

左下斜め
[   ][ 5 ]
[ 5 ][   ]        有効
```

斜めは公式文章で認められるものの、45度の直線に限るか、変則的な折れ線を含むかは明文化されていない。通常のグリッド解釈と公式画像から、45度の二方向と考えるのが妥当である。

### 削除済みセル越し

公式ヒント画像では、同じ列の二つの「1」が黄色で強調され、その間に薄く表示された削除済みセルがあり、縦の接続線が描かれている。これは、少なくとも縦方向では削除済みセルを挟んだ接続が可能であることを示す。citeturn22view1

```text
[ 1 ]  ← 選択
[ × ]
[ × ]
[ × ]
[ 1 ]  ← 接続可能
```

同じ原理が水平・斜めにも適用される可能性は高いが、公式文章だけでは完全には確定しない。オリジナル仕様では全8方向に統一して適用すべきである。

### 未削除数字が途中にある場合

間に未削除数字がある接続を認める公式証拠はなく、ゲームの線視認ルールからも、途中の数字は遮蔽物と考えるのが自然である。

```text
[ 2 ][ × ][ × ][ 8 ]    有効とする根拠あり

[ 2 ][ 5 ][ × ][ 8 ]    5が遮るため無効とするのが妥当
```

Easybrainの内部判定を厳密に検証したものではないため、後者はBから導く仕様推定である。

### 行末と次行頭

公式文章は、行末と次行の行頭を接続できると明記している。citeturn20view0turn20view2

```text
第1行  [ 1 ][ 9 ][ 2 ][ 3 ][ 4 ][ 5 ][ 6 ][ 7 ][ 6 ]
第2行  [ 4 ][ 8 ][ 1 ][ 2 ][ 3 ][ 5 ][ 7 ][ 9 ][ 1 ]
                                            ↑     ↑ではなく
第1行の最終列 6 と 第2行の先頭列 4 が行またぎペア
```

より簡略化すると次のとおりである。

```text
行 r      … [ 6 ]
行 r+1  [ 4 ] …

6 + 4 = 10 なので有効
```

第三者の議論では、「右端の最後の数字から次行左端の最初の数字へ折り返す」「チュートリアルにある」とする利用者投稿がある。ただし、同じスレッド内でも挙動への混乱が見られ、公式仕様の代替にはできない。citeturn23search11

### 盤面を一次元の読み順として扱う可能性

次の二方式は区別しなければならない。

**厳格な行端方式**

```text
行 r の col=8 と、行 r+1 の col=0 のみ接続
```

**一次元読み順方式**

```text
行 r      … [ 6 ][ × ][ × ]
行 r+1  [ × ][ × ][ 4 ] …

間の一次元セルがすべて空なら 6 と4を接続
```

公式文章が直接保証するのは前者に近い。「削除済みの行端セルを飛ばして、行末側の最後の生存数字と次行側の最初の生存数字を結ぶ」一般化については未確認である。

「Master Ten」では曖昧さをなくすため、以下のどちらかを仕様書で明示しなければならない。本報告書の推奨は、後述の**一次元読み順方式**である。

### 空行

完全に空の行を接続判定上残すか、即時削除するかは公式には確認できない。公式の「行を取り除くと得点」という記載から、空行の削除処理は存在すると推定できるが、判定タイミングはDである。citeturn20view0

## 数字追加・操作・補助機能

**数字追加**

### ボタンを使う条件

Easybrainの公式説明は、「手がなくなった場合」「手詰まりになった場合」に残存数字を下部の追加行へ加えられるとしている。citeturn20view0turn20view1

したがって、「有効手が0のとき追加できる」はAである。

一方、手が残っていても任意に追加できるかは明記されていない。追加ボタンは通常画面で常時表示されるように見えるが、表示されていることと操作可能であることは同じではない。citeturn22view0

| 項目 | 結論 | 確認度 |
|---|---|---:|
| 手詰まり時に追加可能 | 公式確認 | A |
| 手が残っている時にも追加可能 | 未確認 | D |
| 追加ボタンの常時表示 | 公式画像で観察 | B |
| 追加前に自動で手詰まり判定 | 可能性あり | D |

### 複製対象と順序

公式説明は「remaining numbers」を追加するとしているため、すでに削除された数字は複製対象ではなく、残存数字が対象になると読むのが自然である。citeturn20view0

ただし、次の詳細は公式には確認できない。

| 詳細 | 確認度 | 備考 |
|---|---:|---|
| 上から下、左から右の読み順で複製 | D | 最も自然だが未確認 |
| 行単位で別々に複製 | D | 未確認 |
| 生存数字だけを詰めた列として複製 | D | 未確認 |
| 削除済みセルの位置も空所として複製 | D | “remaining numbers”からは可能性が低い |
| 最終行の途中から連続して追加 | D | 未確認 |
| 常に新しい完全な行から追加 | D | 未確認 |

類似ゲームでは、残存数字を読み順のまま複製する方式が一般的に見られるが、別製品やクローンの仕様をEasybrain製品の確定仕様として採用すべきではない。

### 追加先と列数

公式文言は「additional lines at the bottom」「extra lines at the bottom」であり、過去にできた空所を埋めるのではなく、盤面下部へ追加すると解釈できる。citeturn20view0turn20view3

したがって、過去の削除穴を埋める可能性は低いが、厳密な内部挙動はB/Dである。

列数については、追加後も同じ盤面幅を維持するのが公式画像とゲーム構造から自然であり、9列のままと推定される。追加によって列数が変わる証拠はない。

### 追加可能回数と上限

公式画像では、追加ボタンの上に「4」と読める青いバッジが表示されている。これは残り回数または所持アイテム数を示す可能性が高い。citeturn22view0turn22view1

ただし、「初期5回、使用後4回」とは断定できない。バッジが広告視聴や通貨で増減するリソースである可能性、ステージごとに異なる可能性もある。

| 項目 | 結論 | 確認度 |

## オリジナル仕様・問題生成方式

**オリジナルゲームで採用すべき仕様**

以下はEasybrainの仕様を断定するものではなく、「Master Ten」用に曖昧さを排除した推奨仕様である。

### 盤面

| 項目 | 推奨仕様 |
|---|---|
| 列数 | 9列固定 |
| 数字 | 1～9 |
| 初期行数 | 通常6～9行、Master 8～12行 |
| 空所 | 値0として保持 |
| 部分消去 | 詰め直さず位置維持 |
| 全空行 | 即時削除し、下行を上へ移動 |
| 追加後の幅 | 9列固定 |
| 最大論理行数 | 48行を初期上限とし、生成検証で調整 |
| 表示 | 縦スクロール、現在の有効領域へ自動追従 |
| タブレット | 盤面幅に上限を設け中央配置 |

9列を採用する場合でも、Easybrainのセル寸法、配色、書体、余白、ボタン形状を複製せず、独自の視覚体系を使う。

### 合法手

二数字`a`と`b`は、次をすべて満たす場合に消去可能とする。

1. `a == b`、または`a + b == 10`。
2. 同一行、同一列、45度の同一斜線上、または後述の読み順接続にある。
3. 二数字の間にあるセルがすべて空所である。
4. 同じペアを逆順で重複列挙しない。

### 直線接続

各生存セルから8方向へ走査し、最初に遭遇した生存セルだけを候補とする。

```text
[ 2 ][ × ][ × ][ 8 ]   2+8=10、途中は空所 → 有効

[ 2 ][ × ][ 5 ][ 8 ]   最初の生存セルは5 → 2と8は無効
```

この方式なら、未削除数字を飛び越すことがない。

### 読み順接続

「Master Ten」では、行末接続を曖昧にしないため、盤面配列を左上から右下へ読む一次元順序を補助的に使用することを推奨する。

二つの生存セルの一次元インデックスを`i < j`としたとき、`i+1`から`j-1`がすべて空所であり、少なくとも一つの行境界をまたぐ場合、読み順接続候補とする。

```text
行 r       [ 6 ][ × ][ × ]
行 r+1     [ × ][ × ][ 4 ]

一次元順で6と4の間に生存数字なし
6+4=10 → 有効
```

全空行を即時削除するなら、通常は多数行を無制限に飛び越す状態は生じにくい。

### 数字追加

| 項目 | 推奨仕様 |
|---|---|
| 使用条件 | 有効ペアが0のときだけ |
| 複製対象 | 全生存数字 |
| 順序 | 上から下、左から右 |
| 空所 | 対象外 |
| 追加位置 | 現在の論理末尾から連続 |
| 部分最終行 | 空き位置から埋める |
| 過去の穴 | 埋めない |
| Master追加回数 | 原則3回 |
| 通常追加回数 | 3～5回を難易度別設定 |
| 追加操作コスト | 探索上は1手、難易度評価では重く扱う |
| 追加後に上限超過 | その問題を生成不適格とする。プレイ中は敗北扱いも可能 |

追加を有効手が残る間も許すと、探索分岐が急増し、プレイヤーが大量追加で盤面を意図的に変形できる。高難易度パズルとして解法品質を制御するなら、手詰まり時だけに限定する方が適している。

### 終了条件

**勝利**は生存数字0。

**敗北**は、有効ペア0かつ追加残数0。

**生成不適格**は、ソルバーが指定予算内で可解性を証明できない、最大高さを超える、または難易度範囲外の場合とする。

探索タイムアウトは「解答不能」ではなく「UNKNOWN」として扱う。

| テンプレート生成 | テンプレート次第で保証 | 高 | 中 | 軽い | 中 |
| seed付き生成 | seed単独では保証しない | 中 | 低 | 軽い | 高 |
| 生成後ソルバー検証 | 探索モデル内で保証可能 | 高 | 高 | 重い | 高 |
| 固定問題集 | 人手・検証次第で非常に高い | 非常に高い | コンテンツ制作が重い | 実行時は軽い | 低～中 |
| 固定＋生成の混合 | 高い | 非常に高い | 高 | 中～重 | 非常に高い |

### 完全ランダム生成

数字を独立にランダム配置するだけの方式は実装が容易だが、初期有効手0、極端に多い単純ペア、追加しても解けない盤面、ほぼ自明な盤面が混在する。

seedを付けても、再現性が得られるだけで可解性は改善しない。

### 逆向き生成

空盤面または小さな可解盤面から開始し、最終的に消せる数字ペアを逆方向に挿入していく。各逆操作が正しく定義されていれば、少なくとも構築時の逆順が解答経路になる。

課題は、生成時の逆順がプレイヤーに見えやすいこと、追加操作を逆向きに扱いにくいこと、行削除による位置変化を正確に逆算する必要があることである。

### テンプレート生成

高難易度になりやすい局所構造をテンプレートとして持つ。

例として、特定のセルを先に消すと別のペアが遮断される「ゲート」、一つの数字が二つの候補と組める「競合」、行削除後にのみ縦ペアが開く「遅延解放」などがある。

テンプレートだけでは類似感が生じるため、数字置換、左右反転が安全な場合の変形、行ブロック入れ替え、空所位置変形を組み合わせる。

### seed付き生成

同じseedから同じ問題を再現できるため、問題ID、再プレイ、共有、バグ報告、回帰テストに向く。ただし、生成器のバージョンをIDへ含めなければ、生成アルゴリズム変更後に同じseedが別問題になる。

推奨ID例は、概念的に次の情報を持つ。

```text
mode / generatorVersion / ruleVersion / seed / difficultyRevision
```

### 生成後ソルバー検証

候補盤面を作った後、完全または予算付き探索で次を計測する。

| 検査 | 目的 |
|---|---|
| 可解性 | 少なくとも一つの解を確認 |
| 最短手数 | 難易度・品質 |
| 必要追加回数 | モード制約 |
| 最大高さ | UI・メモリ制約 |
| 解答経路数 | 唯一解に近いか |
| 誘惑手 | 誤手による詰み |
| 探索ノード数 | 計算的難しさ |
| 重複盤面ハッシュ | 同型問題の除外 |

探索予算切れは不合格または保留にし、「解けない」とは断定しない。

### 固定問題集

最上位Master問題は固定問題として保存するのが望ましい。固定問題なら、設計者が解答経路、ヒント品質、UI上の視認性、誤手の意味を確認できる。

ただし、公開済みEasybrain問題の配置を大量に転記して固定問題集を作るべきではない。

### 推奨混合方式

推奨パイプラインは次のとおりである。

```text
テンプレートまたは逆向き生成
        ↓
seedによる数字・配置変形
        ↓
高速な予備検査
        ↓
完全ソルバーまたは高予算ソルバー
        ↓
難易度特徴量を計測
        ↓
類似問題・重複問題を除外
        ↓
Master候補だけ人手レビュー
        ↓
固定問題として版管理
```

通常問題は生成問題を多くし、Master上位問題は固定・検証済み問題を中心にする混合方式が、品質と多様性のバランスに優れる。

## ソルバー・難易度モデル・実装要件

**推奨ソルバー設計**

### 状態表現

ソルバー状態には少なくとも次を含める。

| 状態要素 | 必要性 |
|---|---|
| 盤面セル列 | 生存数字と空所 |
| 列数 | 原則9、ルール版に含める |
| 論理長 | 末尾の部分行を区別 |
| 追加残数 | 同じ盤面でも可解性が変わる |
| 追加使用回数 | 難易度・コスト計算 |
| ルール版 | 行削除や行またぎ変更への対応 |
| 履歴 | 探索状態には不要だが解答復元に必要 |
| スコア | 可解性探索には原則不要 |

スコアを状態キーへ含めると同じ盤面が別状態として重複する。スコア目標が勝利条件に関係しない限り、ソルバーの状態から除外する。

### 正規化

ペア削除後、完全空行を削除する仕様なら、毎手後に盤面を正規化する。

末尾の不要な空セルも切り詰める。ただし、部分最終行の長さが数字追加先へ影響するため、`logicalLength`を失ってはいけない。

### 有効手の列挙

各生存セルについて8方向へ走査し、最初に遭遇する生存セルを調べる。その値が同じか合計10なら候補とする。

さらに、一次元読み順接続を別に列挙する。

同一結果を生むペアは、`i < j`で正規化し、生成後状態のハッシュが同じものを一つにまとめる。

単純には全セルから走査できる。性能が不足した段階で、各方向の次生存セル表、行・列・斜線ごとのリンク構造をキャッシュする。

### 数字追加を含む探索

追加操作は通常のペア消去とは異なる遷移である。

```text
有効ペアあり
    → ペア消去だけを列挙

有効ペアなし、追加残数あり
    → 数字追加を唯一の遷移として列挙

有効ペアなし、追加残数なし
    → 未解決終端
```

この設計では追加を任意操作にしないため、分岐数を抑えられる。

### DFS

深さ優先探索はメモリ効率がよく、任意解を早く見つける可能性がある。一方、探索順に強く依存し、単純DFSの最初の解が最短とは限らない。

検証用の「解が一つでもあればよい」高速探索として有用だが、深度上限、循環・重複状態防止、失敗状態メモ化が必須である。

### BFS

各操作を同じ1コストとするなら、幅優先探索は最少操作数の解を得られる。しかし、分岐数が大きい盤面ではフロンティアのメモリ消費が急増する。

初期盤面が小さいテストケース、ソルバーの正しさを確認する基準実装、浅い問題の最短解検証に限定するのが適切である。

### A\*

A\*は`f(n)=g(n)+h(n)`で状態を評価し、許容的なヒューリスティックを使えば最小コスト解を得るための基礎となる。citeturn19search0turn19search3

本ゲームでは、追加がない局面なら、残存数字数を2で割った値が、残りペア消去回数の下界になる。追加が将来発生すると数字数が増えるため、より精密な下界は難しい。

A\*は最短解や追加回数を重く罰する重み付き解を得たい場合に有効だが、OPEN集合とCLOSED集合が大きくなりやすい。

### IDA\*

IDA\*は、A\*型の評価値に閾値を置き、深さ優先探索を閾値を増やしながら繰り返す。Korfの反復深化研究は、指数的探索木におけるメモリ効率と最適解探索を扱っている。citeturn24search1turn24search4turn24search7

本ゲームでは、A\*のメモリ使用が問題になる場合の有力候補である。ただし同じ浅いノードを再探索するため、反復間キャッシュ、手順序付け、失敗状態表が重要になる。

### 推奨構成

| 用途 | 推奨アルゴリズム |
|---|---|
| 小盤面の正解基準 | BFSまたはDijkstra |
| 任意解の高速発見 | 手順序付け付きDFS |
| 最短手数 | A\*、小規模ならBFS |
| メモリ制限下の最短解 | IDA\* |
| 大量候補の生成検査 | 二段階の有界DFS＋IDA\* |
| ヒント | 解経路キャッシュ、失効時に時間制限探索 |
| 解答経路数推定 | 深度上限付き列挙またはDP |
| 完全な解答不能証明 | 状態空間を尽くす探索。予算切れはUNKNOWN |

### メモ化と状態ハッシュ

状態キーは盤面、論理長、追加残数、ルール版から作る。

高速化にはZobrist型ハッシュを利用できる。Zobrist hashingは、盤面状態をハッシュ化して、同一局面の再探索を避けるトランスポジションテーブルに使われる代表的手法である。citeturn19search17turn19search2

ただし64ビットハッシュには理論上衝突がある。検証用ソルバーでは、ハッシュだけで同一性を断定せず、必要に応じて圧縮済み実状態または二重ハッシュで確認する。

TypeScriptでは、正確性を優先する基準版として文字列・バイト列キーを用意し、最適化版で64ビット相当のハッシュへ移行するのが安全である。

### 対称性除去

盤面は行またぎ接続、数字追加順、行削除のため、回転・左右反転を無条件に同一視できない。

安全な重複除去は次に限定する。

- 同じ二セルを逆順で選んだ手。
- 異なるペア選択が完全に同じ正規化後状態を生む場合。
- 生成器が対称変形もルール保存すると事前に証明できるテンプレート。

安易な回転対称性除去は不正解を招く。

### 枝刈り

有効な枝刈り候補は次のとおりである。

| 枝刈り | 内容 |
|---|---|
| 失敗状態キャッシュ | 既に解なしと証明した状態を再探索しない |
| 経路内重複 | 現在の探索経路に同じ状態があれば打切り |
| 同一結果統合 | 異なる手が同一盤面を作る場合、一つだけ探索 |
| 深度上限 | 規定手数を超えた枝を切る |
| 高さ上限 | 許容最大行数超過を切る |
| 追加上限 | モード制限超過を切る |
| 手順序付け | 行消去、拘束された数字、解キャッシュ手を優先 |
| 到達不能条件 | 有効手なし・追加なしを即失敗 |
| 奇偶条件 | 追加が今後ない状態で生存数が奇数なら失敗 |

生存数の奇偶枝刈りは、追加操作が残っている場合にはそのまま使えない。数字追加が生存数を増やし、奇偶を変える可能性があるためである。

### 探索上限と解答不能判定

探索結果を三値にする。

| 結果 | 意味 |
|---|---|
| SOLVED | 解経路を発見 |
| UNSOLVABLE | 許可された全状態を探索して解なしを証明 |
| UNKNOWN | 時間、ノード、メモリ上限に到達 |

問題生成ではUNKNOWNを公開問題として採用しない。

提案上限は、開発環境で問題候補一件あたり数秒、クライアントの即時ヒントでは数十～数百ミリ秒、バックグラウンド探索では約一秒程度から計測を開始し、端末性能と盤面規模から調整する。具体値は性能測定前の仮値である。

### 最短解と任意解

任意解は、問題が解けることの最低限の保証に使える。

最短解は、難易度、理想手数、ヒント評価、プレイヤー手順の効率比較に必要である。

追加操作を通常ペアと同じ1手と数えるか、追加に大きなコストを与えるかで「最短」の意味が変わる。推奨コストは次のように二系統で保持する。

```text
主目的：追加回数を最小化
副目的：総操作数を最小化
```

辞書式最適化、または`追加コストを十分大きくする`重み付き探索で扱える。

### ヒント用と検証用

| 要件 | ヒント用 | 問題検証用 |
|---|---|---|
| 応答時間 | 厳しい | 比較的長くてよい |
| 完全性 | 必須でないが安全手が必要 | 原則必要 |
| 最短性 | なくてもよい | 難易度計測では必要 |
| メモリ | 端末制約 | 開発サーバー・ローカル処理可 |
| キャッシュ | 現局面の解経路を保持 | 状態横断の失敗表 |
| 失敗時 | 「解析中」または浅い助言 | 問題を保留・不採用 |
| 出力 | 次の一手＋理由 | 解経路、統計、証明状態 |

ヒントが単に「今消せるペア」を示すだけだと、難問では詰みへ誘導する可能性がある。少なくとも一つの完走経路上にある手を返すべきである。

**推奨難易度モデル**

Easybrainが以下の指標を使っているという公開証拠はない。すべて「Master Ten」独自モデルの提案である。

### 基本指標

| 指標 | 定義 | 解釈上の注意 |
|---|---|---|
| 初期有効手数 | 初期状態の合法ペア数 | 少なすぎると強制手で簡単な場合もある |
| 平均候補手数 | 解答経路または全探索局面の平均分岐数 | 対象局面集合を固定する |
| 最大分岐数 | 一局面の最大合法手数 | 視覚的負荷を反映 |
| 探索ノード数 | 重複除去後の展開状態数 | ソルバー・手順序に依存 |
| 解答深度 | 解に到達する操作数 | 追加をどう数えるか明記 |
| 最短解手数 | 最小コスト解 | 客観的な長さ |
| 数字追加回数 | 最適解または全解での追加数 | 高さ・記憶負荷と相関し得る |
| 誘惑手数 | 合法だが解を失う、または大幅に悪化させる手 | 定義を固定する |
| 誤手詰み確率 | 人間モデルが誤手を選んだ後の失敗率 | 人間モデルに依存 |
| 解答経路数 | ルール上の完走経路数 | 手順交換を別解と数えるか決める |
| 強制手割合 | 合法手が1つの解答局面割合 | 高すぎると一本道で簡単 |
| 最大盤面高さ | 解答中の最大行数 | 視認・スクロール負荷 |
| フェーズ難度 | 序盤、中盤、終盤別の指標 | 終盤だけ極端に難しい問題を検出 |
| ノーアシストクリア率 | ヒント・Undoなしの成功率 | 実測データが最重要 |

### 誘惑手の定義

合法手`m`を次のいずれかに該当するとき誘惑手と定義できる。

- 選ぶと解答不能状態になる。
- 選んでも解けるが、最小追加回数が増える。
- 残り最短手数が所定値以上増える。
- 最大盤面高さが大きく悪化する。
- 直近では行を消して魅力的に見えるが、後で必須数字を失う。

「合法手だが最短解に含まれない」だけで誘惑手とすると、複数の少し長い正常解まで誤手扱いするため、詰みまたは明確な悪化を条件に含める方がよい。

### 分岐数の非単調性

初期有効手数が少ないほど難しいとは限らない。

```text
合法手1つ
→ 迷わない強制手で簡単な場合がある

合法手12個
→ 選択肢が多いが、多くが安全なら簡単な場合がある

合法手6個、そのうち5個が詰み
→ 強い誘惑を伴い難しい
```

したがって、分岐数と誘惑率の相互作用を測る。

### 独自難易度スコア

各指標を問題コーパス内の中央値と四分位範囲でロバスト正規化し、極端値を制限する。

例として、次の生スコアを提案する。

```text
R =
  0.22 × log探索ノード数
+ 0.14 × 最短解手数
+ 0.12 × 最小追加回数
+ 0.12 × 誤手詰み確率
+ 0.10 × 誘惑手割合
+ 0.08 × 最大盤面高さ
+ 0.08 × 最大分岐数
+ 0.08 × 分岐エントロピー
+ 0.06 × フェーズ偏り
- 0.10 × 強制手割合
- 0.12 × log解答経路数
```

各項は正規化後の値とし、最終的にシグモイド等で0～100へ写像する。

```text
difficulty = round(100 / (1 + exp(-R)))
```

係数は初期案であり、プレイデータから再学習する。

### 推奨難易度帯

| スコア | 名称案 | 特徴 |
|---:|---|---|
| 0～24 | Starter | 有効手が見つけやすく追加不要 |
| 25～44 | Skilled | 一部順序依存 |
| 45～64 | Expert | 追加または先読みが必要 |
| 65～79 | Master | 誘惑手・低解答数・複数段階の解放 |
| 80～94 | Grandmaster | 高探索量、低クリア率、厳しい順序依存 |
| 95～100 | Research | 人手レビュー必須。理不尽さの危険あり |

高スコアが必ず良問とは限らない。視認困難、極端なスクロール、長すぎる一本道、単なる総当たりを高難度と誤認しない品質規則が必要である。

### Master相当の採用基準

「Master Ten」のMaster問題は、例えば次を満たす候補から選ぶ。

| 指標 | 提案範囲 |
|---|---|
| 難易度スコア | 70以上 |
| 可解性 | SOLVED、可能なら最適性証明済み |
| 最小追加回数 | 1～3回程度 |
| 解答経路 | 少数だがゼロでない |
| 誘惑手 | 複数存在 |
| 強制手割合 | 極端に高すぎない |
| 最大高さ | UI上限内 |
| 初期手 | 少なくとも1つ |
| 人手レビュー | 必須 |
| ヒント | 全局面で安全な次手を返せる |

### ヒントなしクリア率の推定

リリース前は、複数の擬似プレイヤーを使う。

| エージェント | 人間行動の近似 |
|---|---|
| ランダム合法手 | 下限的な基準 |
| 行消去優先 | 短期報酬志向 |
| 追加回避 | 保守的プレイヤー |
| 深さ2～4の先読み | 中級者 |
| 完全ソルバーに確率的誤りを付与 | 上級者 |
| 過去手の記憶制限付き | 人間的見落とし |

リリース後は、難易度帯、初回挑戦・再挑戦、ヒント、Undo、端末サイズ等を分け、ノーアシスト成功率を測る。問題ごとの試行数が少ない段階では、同じ難易度帯の事前分布を共有する階層的な推定が有用である。

**Codexに渡す実装要件**

以下はコードではなく、実装指示書として渡すべき要件である。

### ルールエンジン

| ID | 要件 |
|---|---|
| RULE-PAIR | 同値または合計10のみ有効 |
| RULE-RAY | 横、縦、斜め8方向の最初の生存セルだけを候補化 |
| RULE-BLOCK | 途中の生存セルを飛び越えない |
| RULE-WRAP | 一次元読み順で中間が全空所なら行境界越し候補 |
| RULE-DELETE | ペア成立時に2セルを空所化 |
| RULE-ROW | 全空行を削除し下行を上へ移動 |
| RULE-ADD | 有効ペア0のときのみ追加可能 |
| RULE-COPY | 生存数字を行優先順で複製 |
| RULE-APPEND | 論理末尾から追加し、過去の穴は埋めない |
| RULE-WIN | 生存数字0で勝利 |
| RULE-LOSE | 有効ペア0かつ追加残数0で敗北 |

### 決定論

同じ初期盤面、同じルール版、同じ操作列から、必ず同じ盤面が得られること。

乱数はUI演出と問題生成で分離すること。

問題IDに生成器版、ルール版、seedを含めること。

### ソルバーAPIの責務

- 合法手を重複なく列挙する。
- 盤面へ手を適用して新状態を返す。
- 元状態を破壊しない純粋な遷移版を用意する。
- 数字追加を探索遷移へ含める。
- SOLVED、UNSOLVABLE、UNKNOWNを区別する。
- 解答手順、展開ノード数、最大深度、所要時間を返す。
- 最短解探索と任意解探索を別モードにする。
- ヒントでは安全な解経路上の次手を返す。
- ハッシュ衝突検証を無効化できない検証モードを用意する。

### 問題生成パイプライン

- seedから候補を再現可能にする。
- 初期生存数を偶数にする。
- 初期有効手0の候補を原則除外する。
- 最大追加回数内で可解であることを検証する。
- 最大行数を超える解しかない候補を除外する。
- 難易度特徴量を保存する。
- 初期盤面と正規化盤面のハッシュで重複を除外する。
- 解答経路を内部検証データとして保存する。
- 公開データには必要最小限の情報だけを含める。
- 生成器更新後も旧問題を再現できるよう版を固定する。

### UI

- 1セル目と2セル目の状態を明確に区別する。
- 色だけでなく輪郭、形、アニメーションでも状態を示す。
- 削除セルを視認可能な薄い記号にするか、完全空白を選択可能にする。
- 手詰まり時に数字追加ボタンを強調する。
- 手が残る場合は追加ボタンを無効化し、理由を表示する。
- ヒント使用時は、ペアと経路を示す。
- Undo、ヒント、リスタート使用を結果へ記録する。
- スクロール後も選択セルを見失わない。
- 縮小しすぎず、セル外側のタップ領域を広く取る。
- 振動と効果音を個別に無効化できるようにする。

### 保存

保存対象は、問題ID、ルール版、盤面、論理長、追加残数、手履歴、アシスト使用履歴、経過時間、難易度版である。

保存データ読込時には、配列長、値範囲、ハッシュ、ルール版を検証する。
