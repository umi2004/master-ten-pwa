# Master Ten アーキテクチャ

## 1. 目標

Master Ten は、外部サーバーなしで動く Vanilla TypeScript の静的PWAである。ルール判定、探索、問題データ、保存、DOM UIを明確に分離し、同じ入力から同じ結果が得られる検証可能な構成にする。

## 2. 技術構成

- Vite + TypeScript + HTML + CSS
- Vitest（Node環境の単体・統合テスト）
- Vanilla TypeScript。UIフレームワークは使用しない。
- Service Worker は自前の小さな実装とし、ビルド成果物と固定問題を同一オリジンでキャッシュする。
- GitHub Actions で `npm ci`、`npm test`、`npm run build`、GitHub Pagesデプロイを行う。
- 実行時CDN、外部フォント、広告、分析、認証、外部APIを使用しない。

## 3. モジュール境界

```text
src/core       型、盤面、正規化、合法手、数字追加、状態遷移、版
src/solver     状態キー、基準BFS、実用DFS、結果・統計
src/hints      解経路キャッシュ、安全ヒント
src/puzzles    固定問題、メタデータ、読込時検証
src/generator  seed PRNG、テンプレート変形、開発時評価
src/storage    スキーマ、検証、マイグレーション、localStorage
src/ui         画面、DOM描画、入力、アクセシビリティ
src/styles     トークン、レイアウト、状態、アクセシビリティ
scripts        問題生成・全件検証（アプリ起動時には実行しない）
tests          単体・統合・問題コーパス検証
public         manifest、アイコン、静的PWA資産
```

依存方向は `ui/storage/hints/solver/puzzles -> core` とし、`core` はDOM、localStorage、時間、乱数へ依存しない。

## 4. ルールエンジン

- `Board` と `GameState` は呼び出し元が所有する不変値として扱う。
- 遷移関数は入力配列・履歴を変更せず、新しい配列と状態を返す。
- 合法手列挙はインデックス正規順と状態遷移順を固定し、乱数を使わない。
- ペア消去と数字追加は別関数。共通の `applyGameMove` が型で振り分ける。
- 正規化はペア消去直後だけでなく、初期状態生成時にも明示的に行い、状態キーは正規形だけを受け取る。
- 開発時アサーションで `cells.length === logicalLength`、セル範囲、幅、追加残数を検証する。

## 5. ソルバー

### 5.1 状態キー

正確性優先の文字列キーを使用する。

```text
ruleVersion|logicalLength|additionsRemaining|cellsを区切った列
```

盤面、論理長、追加残数、ルール版を必ず含める。スコア、UI選択、経過時間、ヒント回数は可解性を変えないため含めない。文字列全体で比較し、短いハッシュだけで同一性を断定しない。

### 5.2 基準実装

小盤面用にBFSを用意する。全操作を1コストとして最短操作数を返し、状態空間を尽くした場合だけ `UNSOLVABLE` とする。これは回帰テストと実用ソルバーの可解性照合に使う。

### 5.3 実用実装

初期版はメモ化付き深さ優先探索を採用する。

- 解を早期発見しやすく、ブラウザでのメモリ上限を管理しやすい。
- 経路内状態集合で循環を防ぎ、完全探索済みの失敗状態をメモ化する。
- 手順序は決定論的。行削除数が多い手、残存数が少ない後状態、インデックス順で並べる。
- ノード、時間、深度のいずれかの上限で打ち切ったら `UNKNOWN`。
- 上限に触れず全分岐を尽くした場合だけ `UNSOLVABLE`。
- 解手順は親経路から復元し、再適用テストを行う。

IDA* は最適解と低メモリを両立する有力候補だが、初期版で基準BFSとの比較可能性を優先し、複雑なヒューリスティックを品質ゲートにしない。公開問題の最適性証明や生成速度が不足した場合に、同じ `Solver` 契約の追加実装として導入する。A* はOPEN集合のメモリ消費が9列・可変行盤面で大きくなり得るため、小盤面と評価用途に限定する。

### 5.4 結果契約

`status`, `solution`, `nodesExpanded`, `maxDepth`, `elapsedMs`, `terminationReason`, `provenOptimal`, `minimumAdditionsProven` を返す。`terminationReason` は少なくとも solved、exhausted、node-limit、time-limit、depth-limit を区別する。

時間上限判定には単調増加する時計関数を依存注入できるようにし、時間上限テストを決定論的にする。

## 6. ヒント

ヒントキャッシュは `stateKey -> verified solution suffix`。要求時に現状態キーを照合し、先頭手を再度合法性検査して返す。キャッシュ不一致なら実用ソルバーを呼ぶ。結果が `SOLVED` の場合だけ先頭手を安全とみなし、`UNSOLVABLE` と `UNKNOWN` では手を返さない。

## 7. 問題生成と固定データ

生成はNode上の開発時スクリプトだけで実行する。

1. 独自テンプレートまたは逆向き構造を選ぶ。
2. seed付きPRNGでルールを保つ変形を行う。
3. 初期手、偶数生存数、高さを予備検査する。
4. 基準・実用ソルバーで `SOLVED` を確認する。
5. 解を再生し、特徴量を計測する。
6. 完全盤面キーと構造署名で重複除去する。
7. 5問ゲート後に30問へ拡張する。
8. JSONまたはTypeScriptの固定データとして版管理する。

公開アプリは生成器を実行せず、検証済み固定問題だけを読み込む。

## 8. 難易度

探索ノード数単独ではなく、初期手数、平均・最大分岐、解答深度、最小追加、誘惑手、強制手割合、解答経路推定、最大高さ、フェーズ別難度を組み合わせる。係数と閾値は `difficulty-model.md` に版付きで定義する。

## 9. 保存方式

`localStorage` を採用する。30問分の現在状態、履歴、設定、完了一覧は数MB未満を想定し、同期的な各手保存でもデータ量が小さい。IndexedDBより実装・障害回復・手動確認が単純で、外部依存も不要である。

- キーを現行、隔離、設定に分ける。
- 保存前にJSON化し、読込後は型ガードで全項目を検証する。
- `schemaVersion`、全版、問題ID、seed、初期盤面ハッシュ、配列長、セル範囲、論理長、追加数、履歴を検査する。
- 既知の旧版だけ純粋なマイグレーションを通す。
- 移行不能または破損データはタイムスタンプ付き隔離キーへ原文を移し、現行キーを削除してユーザーへ通知する。
- セーブ削除は確認ダイアログ後に、Master Tenが所有する接頭辞のキーだけを対象にする。

## 10. UIとアクセシビリティ

- DOMは画面単位で再描画し、状態は単一のアプリコントローラーが所有する。
- 盤面はCSS Gridの9列。標準表示はビューポート幅内へ収める。
- 盤面セルは狭い端末で44px未満になる設計例外を明記し、周囲の操作ボタンは44px以上を確保する。
- 「大きく表示」はセルを44px以上にし、盤面コンテナのパンを許可する。
- 選択、ヒント、フォーカスは色に加え、太枠、内側記号、形状で示す。
- キーボードは矢印移動、Enter/Space選択、Escape解除を提供する。
- safe area、画面拡大、`prefers-reduced-motion`、高コントラストを尊重する。
- 効果音はWeb Audioで短い独自合成音を生成できるが、初期値は控えめにし設定で無効化する。外部音声は使わない。

## 11. PWAとGitHub Pages

- Vite `base` は `/master-ten-pwa/`。
- manifest `start_url` と `scope` も `/master-ten-pwa/` 配下。
- Service Worker URLは `import.meta.env.BASE_URL` から構築する。
- キャッシュ名にアプリ版を含め、activateで同接頭辞の旧キャッシュだけ削除する。
- HTMLはnetwork-firstかつキャッシュfallback、版付きJS/CSS/問題データはcache-firstとする。
- Service Worker更新でlocalStorageへ触れず、セーブを維持する。

## 12. セキュリティとプライバシー

外部通信を行うコードを設けない。GitHub Pagesから同一オリジンの静的資産だけを取得する。ユーザー入力をHTML文字列として挿入せず、`textContent` と属性APIを使う。秘密情報をビルドへ含めない。
